# @monadiam/infra

Shared infrastructure for MonadIAM services: Apache Kafka for inter-service messaging, HashiCorp Vault for shared secrets/crypto, service-owned PostgreSQL/Redis dev infrastructure, ClickHouse as the WORM-style mid-term archive store for audit/change logs, MinIO as the COLD long-term archive those logs age out into, and Grafana + Prometheus + Loki for monitoring. Deployed once per environment and shared by every service repo through a small set of Docker networks plus shared TLS volumes. Docker networks provide transport only; gRPC uses Consul Connect/Envoy mTLS, while Kafka, PostgreSQL, and Redis use native TLS over Docker networks.

<details>
<summary><strong>Local Deployment</strong></summary>

Make sure Docker and Docker Compose V2 are installed on your system before proceeding.

1. Create shared Docker networks:
```sh
make network name="monitoring-network"
make network name="consul-net"
make network name="kafka-net"
make network name="vault-net"
```
`postgres-net` and `redis-net` are not created manually: infra compose owns them and declares them as `internal: true`.
The shared Vault CA volume (`vault_ca` by default) and service TLS volume (`service_tls` by default) are created and populated by this repo on first `make up`; consuming services mount them as external read-only volumes. Vault's own HTTPS bootstrap certificate is generated locally, while Kafka/PostgreSQL/Redis/app-client TLS certificates are issued by Vault PKI.

2. Generate `.env` from example and fill in real values (there is no `.vault.env` for this repo anymore - every secret this repo used to seed by hand is now generated by Terraform, see the Vault section below):
```sh
make env
```
3. Start all services in detached mode:
```sh
make up
```
On a genuinely first boot this also: generates a local self-signed CA + Vault server certificate (`vault-tls`, written to `secrets/tls/` - gitignored), initializes Vault and unseals it (`vault-init-unseal`, writes the root token and Shamir unseal key to `secrets/init-keys/` - also gitignored, see the Vault section for why this is a deliberate, temporary simplification), then runs `terraform-apply`, which provisions the shared Vault instance (mounts, policies, AppRole roles, Transit keys, Database Secrets Engine, generated passwords, and PKI roles). After Terraform, `service-tls` issues Kafka/PostgreSQL/Redis/app-client TLS material through the `pki-service` Vault PKI mount into `service_tls`. First boot takes longer than before while Terraform downloads providers and pulls the OpenSSL helper image if it is not already present.

Compose is split by responsibility. `docker-compose.yml` at the repo root is just an `include:` manifest wiring the domain files together (Docker Compose 2.20.3+) - `make`/`docker compose` pick it up automatically from this directory, no `-f` flags needed:

| File                                  | Owns                                                      |
|:--------------------------------------|:----------------------------------------------------------|
| `docker-compose.yml`                  | Root manifest - only `include:`s the files below           |
| `secrets/compose.yml`                 | Vault, Terraform apply                                     |
| `mesh/compose.yml`                    | Consul, Consul Connect CA/intentions                       |
| `services/identity/compose.yml`       | Identity Patroni/Postgres cluster, Redis, its own Postgres HAProxy |
| `services/access-control/compose.yml` | AccessControl Patroni/Postgres cluster, Redis, its own Postgres HAProxy |
| `services/notification/compose.yml`   | Notification Patroni/Postgres cluster, Redis, its own Postgres HAProxy |
| `messaging/compose.yml`               | Kafka, Kafka UI, Kafka Connect, Debezium init                |
| `observability/compose.yml`           | Grafana, Prometheus, Loki, OpenTelemetry Collector, Tempo    |
| `audit-archive/compose.yml`           | ClickHouse, MinIO, audit archive init/jobs                   |

4. Verify Kafka is running:
```sh
make logs
```
5. Copy each service's own provisioner token `terraform-apply` generated into that service's `.env` (`VAULT_PROVISIONER_TOKEN` - a different value per service, each scoped to only that service's own AppRole role):
```sh
make provisioner-token service=identity-service
make provisioner-token service=access-control-service
make provisioner-token service=notification-service
```
Each run copies that service's token straight to the clipboard (macOS `pbcopy`) - paste it into `VAULT_PROVISIONER_TOKEN` in the matching service's `.env`. See each service's own README for where this goes - this is still a manual copy-paste step at this stage (no CI/CD apply pipeline yet), same as this repo's Terraform config being the hand-maintained source of truth for what each service needs (see Vault section). Nothing else needs copying: each service's own `docker/vault/bootstrap.sh` resolves its AppRole `role_id` directly from Vault at container startup using `VAULT_APPROLE_NAME` (already in `.env.example`) and this same provisioner token.

Service repos attach to them as external pre-existing networks, but they are treated only as encrypted transport for native PostgreSQL and Redis TLS.

| Network              | Env var                     | Default              | Used by                                                                                                                                             |
|:---------------------|:----------------------------|:---------------------|:----------------------------------------------------------------------------------------------------------------------------------------------------|
| `kafka-net`          | `DOCKER_NETWORK_KAFKA`      | `kafka-net`          | Kafka, service app                                                                                                                                  |
| `monitoring-network` | `DOCKER_NETWORK_MONITORING` | `monitoring-network` | Grafana, Prometheus, Loki, service app                                                                                                              |
| `vault-net`          | `DOCKER_NETWORK_VAULT`      | `vault-net`          | Vault, each service's `bootstrap`/`vault-agent`, and each service's own Postgres HAProxy for Vault's Database Secrets Engine                        |
| `consul-net`         | `DOCKER_NETWORK_CONSUL`     | `consul-net`         | Consul (shared DCS and Connect control plane), infra-owned Patroni/Postgres nodes, each service's own Postgres HAProxy, service sidecars             |
| `postgres-net`       | `DOCKER_NETWORK_POSTGRES`   | `postgres-net`       | Internal native-TLS Postgres transport: service apps, Patroni nodes, per-service `<service>-postgres-haproxy`, Kafka Connect/Debezium |
| `redis-net`          | `DOCKER_NETWORK_REDIS`      | `redis-net`          | Internal native-TLS Redis transport: service apps and service Redis nodes                                                                           |

Named Docker volumes owned by this repo and mounted read-only by consuming services:

| Volume              | Env var                     | Default           | Used by                                                                  |
|:--------------------|:----------------------------|:------------------|:-------------------------------------------------------------------------|
| `vault_ca`          | `DOCKER_VOLUME_VAULT_CA`    | `vault_ca`        | Public Vault CA certificate (`ca.crt`)                                   |
| `service_tls`       | `DOCKER_VOLUME_SERVICE_TLS` | `service_tls`     | Vault PKI CA, app client cert/key, Kafka/Postgres/Redis server certs |

**Connecting a consuming service:**
Add the ones it needs to that service's own `docker-compose.yml`:
```yaml
networks:

        external: true
        name: ${DOCKER_NETWORK_MONITORING:?}
    postgres_net:
        external: true
        name: ${DOCKER_NETWORK_POSTGRES:?}
    consul_net:
        external: true
        name: ${DOCKER_NETWORK_CONSUL:?}
    kafka_net:
        external: true
        name: ${DOCKER_NETWORK_KAFKA:?}
    redis_net:
        external: true
        name: ${DOCKER_NETWORK_REDIS:?}
    vault_net:
        external: true
        name: ${DOCKER_NETWORK_VAULT:?}

volumes:
    service_tls:
        external: true
        name: ${DOCKER_VOLUME_SERVICE_TLS:?}
    vault_ca:
        external: true
        name: ${DOCKER_VOLUME_VAULT_CA:?}
```

<summary><strong>Kafka</strong></summary>

Kafka runs as one KRaft broker with broker+controller roles combined. The broker is not published to the host; service clients connect only through `kafka-net`.

**Internal connection *(Docker Network)***
- *Broker address:* `kafka:29092`
- *Protocol:* `SASL_SSL`
- *SASL mechanism:* `SCRAM-SHA-512`
- *mTLS:* required (`ssl.client.auth=required`)
- *Server TLS material:* `service_tls/kafka.pem`, issued by Vault PKI role `kafka-server`
- *Client TLS material:* `service_tls/client.crt`, `service_tls/client.key`, `service_tls/ca.crt`
- *Secret file access:* Kafka Vault Agent outputs and Kafka/client PEM private-key material are group-readable by GID `10000` with mode `0440`; Kafka, Kafka init, Kafka UI, Kafka Connect, `vault-agent`, and `service-tls` join that supplemental group through Compose `group_add`
- *Kafka principals:* `identity-service`, `access-control-service`, `notification-service`, `kafka-connect`, `kafka-ui`, `clickhouse`, plus broker/admin principals
- *ACL model:* `StandardAuthorizer` with explicit topic/group ACLs from `messaging/init-topics.sh`; `allow.everyone.if.no.acl.found=false`

Kafka UI is still published on `http://localhost:${KAFKA_UI_PORT}`. It uses login form auth with user `dev_kafka_admin`; the password is generated by Terraform in `infra-kv/infra/kafka` and rendered into the Kafka UI config by the infra Vault Agent.

When migrating an existing local stand from the old PLAINTEXT Kafka configuration, reset Kafka storage before first secure start. SCRAM bootstrap users are written during `kafka-storage.sh format`; an already formatted `kafka_data` volume will not receive them automatically.

<summary><strong>Vault</strong></summary>

A single shared Vault instance is run from this repository and used by all services, on `vault-net`. **This repository owns all provisioning** - mounts, policies, AppRole/Kubernetes auth roles, Transit keys, Database Secrets Engine connections/roles, the AWS Secrets Engine role, and every generated password - declared once in `secrets/terraform/` and applied by the `terraform-apply` container on every `make up`. A service repository no longer creates its own policies or KV entries; it only ever *consumes* what this repo already provisioned for it. `secrets/terraform/locals.tf` is the single manifest of what every service needs, kept in sync by hand with each service repo (a PR here, whenever a service's secret needs change - no automated sync exists at this stage).

- *Address (Docker network):* `vault:8200` (TLS, see below)
- *Address (host machine):* `https://localhost:8200`
- *Storage:* Raft (Integrated Storage), persistent volume `vault_data` - Vault no longer loses its state on restart.
- *Vault HTTPS TLS:* self-signed for the local compose stand, generated once by `vault-tls` into `secrets/tls/` (gitignored). The public CA cert is copied into `DOCKER_VOLUME_VAULT_CA` (`vault_ca` by default); Vault HTTPS private keys remain local to this repo.
- *Unseal:* `vault-init-unseal` owns only local compose init/unseal. It initializes Vault once, writes the Shamir unseal key and initial root token to `secrets/init-keys/` (gitignored), and then keeps Vault unsealed after restarts. If Vault storage is fresh but old key files remain, it refuses to initialize again.
- *Provisioning boundary:* `terraform-apply` is the only stage that reads the local root token. It provisions mounts, policies, auth roles, generated secrets, Database Secrets Engine config, Transit keys, PKI issuers, and scoped handoff tokens. Runtime stages consume only scoped tokens from `secrets/terraform/.output/`.
- *PKI model:* `pki-root` is the root CA mount, `pki` is the Consul Connect intermediate mount, and `pki-service` is the native TLS intermediate mount. Each mount has one configured default issuer. Kafka/PostgreSQL/Redis/app-client roles set `issuer_ref` explicitly to the service TLS issuer.
- *Service native TLS:* `service-tls` uses only `service-tls-issuer-token` to issue leaf certificates. It cannot read root token or CA endpoints. The CA bundle written to `service_tls/ca.crt` comes from Terraform output `service-tls-ca.crt`, derived from the PKI chain Terraform applied. It writes `ca.crt`, `client.crt/key`, `client.pem`, `kafka.crt/key`, `kafka.pem`, `postgres.crt/key`, and `redis.crt/key` into `DOCKER_VOLUME_SERVICE_TLS` (`service_tls` by default).
- *Vault Database engine TLS:* Vault mounts the separate `service_tls_ca` volume read-only and uses only `/service/ca/ca.crt` to verify Postgres through each service's own `<service>-postgres-haproxy`. Vault does not mount the `service_tls` private-key volume.
- *Vault Agent bootstrap:* `vault-bootstrap` no longer reads the root token. It uses `infra-agent-bootstrap-token` only to read the `infra` AppRole role id and mint one secret id for `vault-agent`.
- *Full reset:* `make clean` removes named Docker volumes (including `vault_data`, the shared Vault CA volume, and the service TLS volume), the host-bind-mounted Vault bootstrap state in `secrets/tls/` and `secrets/init-keys/`, and local Terraform runtime state/output in `secrets/terraform/terraform.tfstate*`, `.terraform.tfstate.lock.info`, and `.output/`. If you run `docker compose down -v` by hand without removing those files/directories, `vault-init-unseal` will refuse to blindly re-init because old key files would point at now-gone Raft state. Run `make vault-reset` for a Vault/service-TLS-only reset.

**How a service authenticates to Vault** (see `secrets/terraform/auth.tf`): AppRole in plain docker-compose dev, Kubernetes auth (via Vault Agent Injector) on k3s stands - same policies either way, only the auth backend differs. Each service's own `docker/vault/bootstrap.sh` mints a one-time-use `secret_id` for its AppRole role using `VAULT_PROVISIONER_TOKEN` (copied from `secrets/terraform/.output/provisioner-token-<service>` after apply - see step 5 above), then a `vault-agent` sidecar in that service's `docker-compose.yml` logs in with it and renders secrets to disk, auto-renewing. Each service gets its own `VAULT_PROVISIONER_TOKEN`, scoped by policy to mint `secret_id`s only for that service's own AppRole role (and, for identity-service, its `identity-service-key-trim` role too) - it cannot read or write any actual secret, and it cannot impersonate another service's role.

**Dynamic Postgres credentials** (see `secrets/terraform/database.tf`): the application no longer connects with a static password. Vault's Database Secrets Engine issues a short-lived username+password pair per connection (`database/creds/<service>-app`, ~1h TTL, auto-renewed by that service's Vault Agent) that inherits the admin user's privileges via Postgres role membership (`IN ROLE`). A separate `database/creds/<service>-developer-readonly` role (SELECT-only, ~30m TTL) exists for ad hoc human access - e.g. pulling a fresh, temporary credential into DBeaver. The admin/root Postgres password itself is Terraform-generated, never typed by a human, and used only by Postgres's own bootstrap and by Vault's connection config - not by the application.

**Known gaps, not addressed by this configuration:** host-side dev/operator Redis ports remain direct convenience paths outside the runtime mesh (PostgreSQL has no host-published dev port at all - none of the per-service `<service>-postgres-haproxy` containers publish anything to the host), cloud KMS auto-unseal for stand is still pending, and how a *human* authenticates to Vault to use the `developer-readonly` role (OIDC/LDAP/userpass - not yet decided).

</details>

<summary><strong>Consul</strong></summary>

Single shared Consul instance (one server, `bootstrap_expect = 1`), run from this repository, on `consul-net`. Acts as the DCS (Distributed Configuration Store) for every infra-owned Patroni/PostgreSQL cluster and as the local service mesh control plane for Consul Connect/Envoy.

- *Address (Docker network):* `consul:8500`
- *gRPC/xDS address (Docker network):* `http://consul:8502`
- *Address (host machine):* `http://localhost:${CONSUL_UI_PORT}` (default `8500`), UI at `/ui`

Each Patroni cluster has its own scope (`identity-service`, `access-control-service`, `notification-service`). Patroni nodes register themselves directly into Consul's service catalog (tagged `master`/`replica` depending on role); each service's own `<service>-postgres-haproxy` reads that catalog via `consul-template`, scoped to that service's `PATRONI_SCOPE`, and exposes stable native-TLS write/read entrypoints on `postgres-net`. HAProxy is deployed 1:1 with each Patroni cluster rather than centralized, so a routing outage or misconfiguration is contained to one service's cluster.

For service mesh, Consul is bootstrapped with Vault as the CA provider by `consul-connect-ca`. This repo builds `CONSUL_ENVOY_IMAGE` and applies platform intentions through `consul-intentions` (`* -> *` deny plus explicit gRPC allows). Service repositories register their own local `docker/consul/service.hcl` definitions through their own `consul-register`, then run a colocated Envoy sidecar using `network_mode: service:service`. The gRPC path to `access-control-service` is `127.0.0.1:15051` from the client app into its local sidecar, mTLS between sidecars, then `127.0.0.1:50051` inside the access-control container namespace.

Runtime PostgreSQL and Redis are intentionally not Consul L4 upstreams in this compose target. Applications connect directly to their own service's `<service>-postgres-haproxy` (unified write/read ports across services) and to `<service>-redis:6379` over Docker networks, but those paths require native TLS, CA verification, client certificate, and protocol-native auth. Docker networks are transport only, not the security boundary.

`postgres-net` and `redis-net` are declared with `internal: true`. If these networks already exist from an older setup as manually created external networks, remove/recreate them during the next infra reset so Compose can own the internal network lifecycle.

**Known gaps, not addressed by this configuration:** Consul control plane has no ACLs/TLS yet, Compose has no Kubernetes-style NetworkPolicy/transparent-proxy enforcement, multi-VM deployment still needs Consul client agents and host-routable advertised sidecar addresses, and the single Consul node has no quorum - Consul itself is a SPOF for failover, though PostgreSQL keeps serving reads/writes on whichever node was last elected leader even if Consul is briefly unreachable.

</details>

<summary><strong>ClickHouse</strong></summary>

Single shared ClickHouse instance, run from this repository, on `kafka-net` (Kafka ingestion over `SASL_SSL` + client certificate) and `monitoring-network` (metrics). Append-only long-term store for `AuditLog`/`ChangeLog`, replicated from each service's Postgres.

- *Address (Docker network):* `clickhouse:9000` (native), `clickhouse:8123` (HTTP)
- *Address (host machine):* `localhost:9000` (native), `http://localhost:8123` (HTTP), `http://localhost:8123/play`
- *Default database:* `CLICKHOUSE_DB` in `.env`

Schema applied in filename order by `clickhouse-init`, from `audit-archive/clickhouse/schema/*.sql`:

| File        | What                                                                                  |
|:------------|:--------------------------------------------------------------------------------------|
| `001`/`002` | `audit.audit_log`/`audit.change_log` — shared tables, `service` column, 180-day `TTL` |
| `003`       | `audit_writer`/`audit_reader` users + grants                                          |
| `004`       | Kafka-engine queue tables (`audit-log-archive`/`change-log-archive`)                  |
| `005`       | Materialized views, `DEFINER = audit_writer`                                          |
| `006`       | `audit.archive_log` — bookkeeping table for `clickhouse-archiver` (see MinIO section) |

`003`–`006` use `{{writer_user}}`-style placeholders, substituted via `sed` before running — same convention as the Vault HCL policies.

TTL is 180 days, not the retention period itself — ClickHouse is the mid-term investigation surface (WORM via RBAC below), not the final resting place. `clickhouse-archiver` copies each partition into MinIO well before the TTL would reclaim it (see MinIO section); the TTL is a backstop, not the primary deletion path in normal operation.

Producers write to their own `system.outbox` table (transactional outbox pattern) — Debezium's `EventRouter` wraps every row as `{ actionType, payload: {...} }` before it reaches Kafka, same convention as `realm`/`membership`/`blacklist`. `004`'s queue tables ingest that envelope as-is (`actionType String, payload String`); `005`'s MV unwraps `payload` into the real columns via `JSONExtractString`. Producer-side field names inside `payload` match the columns in `001`/`002` exactly (snake_case); `input`/`delta` arrive pre-serialized as a JSON string, not a nested object.

Three identities, not one shared login:

| User                     | Grants              | Purpose                      |
|:-------------------------|:--------------------|:-----------------------------|
| `CLICKHOUSE_USER`        | admin               | schema DDL, break-glass only |
| `CLICKHOUSE_WRITER_USER` | `INSERT`, `SELECT`  | Kafka ingestion              |
| `CLICKHOUSE_READER_USER` | `SELECT`            | Grafana / ad-hoc queries     |

No `ALTER`/`DROP`/`DELETE`/`UPDATE` for writer/reader — never granted, not revoked. That's what enforces WORM, not the storage engine.

Passwords come from Vault, not `.env` (see Vault section) — mounted into `clickhouse`/`clickhouse-init` at `/vault/secrets/*`. Usernames stay plain in `.env`.

</details>

<details>
<summary><strong>MinIO</strong></summary>

COLD archive for `audit.audit_log`/`audit.change_log` — where data ends up after it ages out of ClickHouse's 180-day hot window, as Parquet. Single shared MinIO instance, run from this repository, on `kafka-net`.

- *Address (Docker network):* `minio:9000` (S3 API), `minio:9090` (console)
- *Address (host machine):* `http://localhost:${MINIO_API_PORT}` (S3 API), `http://localhost:${MINIO_CONSOLE_PORT}` (console)
- *Buckets:* `MINIO_AUDIT_LOG_BUCKET` (default `audit-archive`), `MINIO_CHANGE_LOG_BUCKET` (default `change-log-archive`) — one per ClickHouse table, both services land in the same bucket (`service` column already discriminates inside the Parquet file, same as in ClickHouse)

Buckets are created by `minio-init` (`audit-archive/minio/init.sh`, `minio/mc` image) with Object Lock enabled at creation time — retrofitting Object Lock onto an existing bucket isn't possible, which is why bucket creation and lock configuration happen in the same script, once. Default retention is set in **COMPLIANCE** mode (not GOVERNANCE): nobody, including root, can shorten it or delete an object early. Retention length equals lifecycle expiry — objects age out of the bucket exactly when WORM protection itself lapses, not before:

| Bucket                     | Retention (`MINIO_*_RETENTION_DAYS`) |
|:---------------------------|:-------------------------------------|
| `audit-archive`            | 1095 days (3 years)                  |
| `change-log-archive`       | 365 days (1 year)                    |

`minio-init` also provisions a least-privilege `archiver` identity (`MINIO_ARCHIVER_ACCESS_KEY`) scoped to `s3:PutObject`/`s3:GetObject` on just these two buckets — no delete, no list, no admin. This is the only credential `clickhouse-archiver` ever sees.

Root credentials (`MINIO_ROOT_USER`, password from Vault) exist solely to bootstrap buckets/policy/user in `minio-init` — nothing else uses them.

</details>

<details>
<summary><strong>clickhouse-archiver</strong></summary>

Daily job (`audit-archive/archiver/`, plain shell loop — no cron daemon, no NestJS: the job is platform-level, not owned by identity-service or access-control-service) that exports ClickHouse partitions into MinIO as Parquet once they're older than `ARCHIVE_AFTER_DAYS` (default 150 — a 30-day margin before the 180-day ClickHouse `TTL`), verifies the export by row count, and records success in `audit.archive_log`.

It never issues `DROP PARTITION` or any other destructive statement against ClickHouse — deletion stays exactly where it already was, the table `TTL`. If the archiver falls behind or breaks, the worst case is a few extra days of ClickHouse storage, not a race against data loss; the margin exists specifically so a stalled job has time to be noticed and fixed before the TTL would otherwise catch up.

Uses `CLICKHOUSE_IMAGE` unmodified (`clickhouse-client` only, no extra tooling) — export, read-back verification, and the eventual queries against archived Parquet from ClickHouse Play UI (`s3()` table function, works for both writing and reading MinIO) all go through the same one binary.

> `mc ilm`/`mc retention` flag names in `audit-archive/minio/init.sh` have shifted across `mc` releases — double-check them against the exact pinned `MINIO_MC_IMAGE` tag before relying on this in production.

</details>
